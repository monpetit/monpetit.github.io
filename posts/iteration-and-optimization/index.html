처음엔 아무 생각 없이 Tail Recursion 예제를 하나 만들었을 뿐이었다. Scheme, 구체적으로 말하자면 Guile Scheme으로 반복적인 표준 출력(stdout)의 출력의 성능을 테스트하기 위해 아주 간단한 코드를 만들어 보았다. Python이나 C 같은 절차적 언어라면 반복문(for, while)으로 만들었겠지만, Lisp 계열의 언어라면 재귀(Recursion)으로 만들어야 멋이 난다.

그래서 2,000,000개의 숫자를 차례로 출력하는 재귀 함수를 만들어 보았다. Scheme의 반복을 재귀로 표현한다는 것은 수학으로 말하자면 수열의 점화식(Recurrence Relation)으로 나타내는 것이다. 등차수열의 초항은 2,000,000이고, 공차는 -1이다. 그리고 재귀 호출의 깊이는 2,000,000이다. 스택이 넘치는 것을 막기 위해 꼬리 재귀(Tail Recursion)으로 작성했다.

단순한 반복문
#

이것을 Scheme으로 구현한 코드는 다음과 같다.

(define (loop-test)
  (let loop ((n 2000000))
    (when (> n 0)
      (display n)
      (newline)
      (loop (- n 1)))))

(loop-test)

그리고 콘솔에서 다음과 같이 실행해 보았다.

$ guile loop-example-guile.scm
2000000
1999999
1999998
...
2
1

단순한 코드이므로 잘못될 일이 없다.

그런데 이렇게 테스트해보니 문득 이런 생각이 들었다.

“현존 최고의 성능을 자랑하는 Chez Scheme으로 같은 코드를 실행하면 과연 Guile보다 빠를까?”

특별한 계산도 없이 단순히 stdout에 숫자만 출력하는 건데도 차이가 날까? 그래서 같은 코들 직접 돌려보았다. 위의 소스 코드는 수정 없이 Chez Scheme으로도 잘 잘 돌아간다.

그런데 예상하지 못한 결과가 나왔다.

$ time guile loop-example-guile.scm > /dev/null
________________________________________________________
Executed in  615.68 millis    fish           external
   usr time  587.87 millis  490.00 micros  587.38 millis
   sys time    4.45 millis  426.00 micros    4.02 millis

$ time scheme --script loop-example-guile.scm > /dev/null
________________________________________________________
Executed in    2.71 secs    fish           external
   usr time    2.08 secs  608.00 micros    2.08 secs
   sys time    0.62 secs  497.00 micros    0.62 secs

이럴 리가 없는데. Chez Scheme이 Guile보다 느릴 리가 없는데.

몇 번을 다시 돌려도 마찬가지였다.

그래서 이번에는 다른 구현체를 가지고 다시 돌려보았다. 같은 코드를 Racket으로 돌려보았다. Racket은 내부적으로 Chez Scheme을 사용하고 있다. 그러니 내 예상으로 Racket과 Chez Scheme의 성능 차이는 크게 나지 않을 것이다.

$ time racket loop-example-racket.rkt > /dev/null

________________________________________________________
Executed in    1.35 secs    fish           external
   usr time    1.24 secs  429.00 micros    1.24 secs
   sys time    0.12 secs  285.00 micros    0.12 secs

점점 재밌는 결과가 나온다. Racket이 내부적으로 Chez Scheme을 사용하고 있는데 Chez보다 더 빨랐다. 어떻게 최적화를 한 것일까? 물론 그래도 Guile보다는 느렸다. 아무래도 Guile이 시스템 프로그래밍에 더 특화되어 있기 때문에 입출력 최적화에 더 많은 공을 들인 게 아닐까 생각된다. 게다가 요즘은 Guile이 JIT를 쓰니까 예전에 비해 확실히 빨라졌다.

출력 버퍼
#

그런데 생각해 보니 이런 식의 단순 비교는 큰 의미가 없을 수도 있었다. 특별한 계산 알고리즘이 들어간 것도 아닌데 어떻게 이렇게 차이가 날 수 있는지 알다가도 모를 일이었다. 그래서 혹시 순정 상태(Vanilla)의 출력 버퍼에 설정에 차이가 나는 것일 수도 있겠다는 생각이 들었다. Guile은 별다른 설정이 주어지지 않아도 기본으로 버퍼링을 통한 출력을 수행하지만, Chez Scheme은 기본적으로 버퍼링을 하지 않을 수도 있었다. 그래서 Chez의 출력 옵션을 찾아보았다. 그리고 역시 출력에 최적화를 이룰 만한 여지가 있다는 사실을 알게 되었다.

Chez Scheme은 디버깅의 편의를 위해 기본적으로 버퍼링하지 않고, 출력을 즉시 표시하도록 설계되어 있다. 즉 (newline)을 사용하면 출력 버퍼가 즉시 비워지고 화면에 출력된다. 이것을 방지하려면 Lock을 걸지 않는 출력 전용 텍스트 버퍼를 만들어 사용하면 된다.

이것이 전용 버퍼를 통한 출력 최적화된 코드이다.

(define (loop-test)
  ;; stdout(파일 디스크립터 1번)을 직접 가리키는, 락이 없는 전용 텍스트 포트를 새로 생성
  (let ([fast-port (transcoded-port (open-fd-output-port 1) (native-transcoder))])
    (let loop ((n 2000000))
      (when (> n 0)
        (display n fast-port)
        (newline fast-port)
        (loop (- n 1))))
    ;; 마지막에 한 번만 남은 버퍼를 비워줌
    (flush-output-port fast-port)))

(loop-test)

다시 실행 시간을 측정해 보면,

time scheme --script loop-example-chez.scm > /dev/null

________________________________________________________
Executed in  340.18 millis    fish           external
   usr time  299.37 millis  394.00 micros  298.98 millis
   sys time   28.88 millis  210.00 micros   28.67 millis

역시 순정 상태에 비해 약 8배 가량의 성능 향상을 이룰 수 있었다.

그런데 Chez만 최적화하면 다른 Scheme 구현체들이 좀 억울하다. 그래서 Guile과 Rakcet도 최적화할 여지가 있는지 살펴보았다. Guile과 Racket은 기본적으로 출력 버퍼링을 수행하고 있다는 점에서 어떤 최적화가 가능한지 살펴보았다.

우선 Racket은 open-output-bytes를 사용하여 출력 버퍼링을 수행하고, 출력 버퍼를 화면에 표시하는 것 또한 FFI를 사용해 최대한 성능을 쥐어짜 보았다.

#lang racket

(require ffi/unsafe)

(define libc (ffi-lib "libc.so.6" #:global? #t))
(define write-func
  (get-ffi-obj "write" libc
    (_fun _int _bytes _size -> _ssize)))

(define (loop-test)
  (let ([buf (open-output-bytes)])
    (let loop ((n 2000000))
      (when (> n 0)
        (display n buf)
        (newline buf)
        (loop (- n 1))))
    (let ([bstr (get-output-bytes buf)])
      (write-func 1 bstr (bytes-length bstr)))))

(loop-test)

그리고 Guile은 이미 버퍼링을 수행하고 있는 상태라, 버피링 방식만 변경했다. 기본 사용안 Line Buffering이 아니라 Block Buffering을 통해서 출력 버퍼를 최대한 저장했다가 한꺼번에 화면에 밀어내는 방식을 썼다.

(define (loop-test)
  (let ([port (current-output-port)])
    (setvbuf port 'block 65536)
    (let loop ((n 2000000))
      (when (> n 0)
        (display n port)
        (newline port)
        (loop (- n 1))))
    (force-output port)))

(loop-test)

그리고 다시 실행 결과를 살펴보았다. Guile과 Racket 모두 순정 상태에 비해 살짝 성능 개선의 효과를 볼 수 있지만, 유의마한 변화를 보았다고는 말하기 어려울 정도였다. 이 두 구현체는 이미 최적화된 상태로 구동되는 거라고 할 수 있다.

결론적으로 최적화 기법의 혜택을 가장 많이 볼 수 있는 구현체는 Chez Scheme이다. 그리고 최적화된 코드로 실행하면 세 구현체 중 가장 빠르다.

입출력의 끝판왕, 그리고 혼란
#

이 정도로 끝내면 좋을 뻔했는데, 이 시점에서

“그렇다면 Scheme 구현체들과 C로 컴파일한 바이너리는 성능에서 얼마나 차이가 날까?”

하는 궁금증이 생겼다. 그래서 같은 일을 하는 C 프로그램을 작성해 보았다.

#include <stdio.h>

int main(void) {
    for (int n = 2000000; n > 0; n--) {
        printf("%d\n", n);
    }

    return 0;
}

그리고 그 결과는 당연히 예상한 대로 나왔다.

$ time ./loop-example > /dev/null

________________________________________________________
Executed in  109.26 millis    fish           external
   usr time  105.29 millis  692.00 micros  104.60 millis
   sys time    4.31 millis  283.00 micros    4.02 millis

최적화 기법을 적용한 Chez Scheme보다도 약 3배 정도 빠르다.

여기까지 왔으니 당연히 끝판왕, Assembly Language를 소환하지 않을 수 없다. 컴퓨터가 낼 수 있는 최대한의 성능을 끌어올린 프로그램은 과연 얼마나 빠를지 궁금해졌다. 그래서 x86-64 어셈블리로 직접 작성한 바이너리를 만들어 보았다.

; loop-example-nasm.asm
; C의 loop-example.c와 동일한 작업:
;   2000000부터 1까지 역순으로 한 줄씩 출력
;;    for (int n = 2000000; n > 0; n--) printf("%d\n", n);
;
; printf를 사용하지 않고 리눅스 write 시스템 콜을 직접 호출하며,
; 숫자를 ASCII 문자열로 변환하는 루틴도 직접 구현
;
; 어셈블리 : nasm -f elf64 loop-example-nasm.asm -o loop-example-nasm.o
; 링크     : ld loop-example-nasm.o -o loop-example-nasm
; 실행     : ./loop-example-nasm

DEFAULT REL                  ; 경고 메시지 방지 (64비트 위치 독립 코드)
BITS 64

section .bss
    buffer resb 16          ; 한 숫자를 변환해 담을 버퍼 (최대 15자리 + 개행)

section .text
    global _start

_start:
    mov rbp, 2000000        ; rbp = n (시작값, unsigned 취급)

.loop:
    ; --- 정수 -> 문자열 변환 (뒤에서부터 채움) ---
    lea rdi, [buffer + 15]  ; 버퍼의 마지막 위치를 가리킴
    mov byte [rdi], 10      ; 맨 끝에 개행 문자 '\n' 고정
    xor ecx, ecx            ; ecx = 자리수(숫자 문자) 개수
    mov rax, rbp            ; rax = 변환할 숫자 n
    mov rbx, 10

.convert:
    xor edx, edx            ; div 전에 edx(상위 32비트)를 0으로 초기화
    div rbx                 ; rax /= 10, 나머지(0~9)는 rdx
    add dl, '0'             ; 나머지를 ASCII 문자로 변환
    dec rdi
    mov [rdi], dl           ; 버퍼(개행 앞)에 숫자 문자 저장
    inc ecx
    test rax, rax           ; 몫이 0이 될 때까지 반복
    jnz .convert

    ; --- write(1, rdi, ecx+1) 시스템 콜 ---
    ; rdi = 숫자 문자열 시작 주소, ecx = 숫자 자릿수, +1 은 개행 문자
    lea rdx, [rcx + 1]      ; rdx = 출력할 바이트 수
    mov rsi, rdi            ; rsi = 출력 버퍼 시작 주소
    mov rax, 1              ; syscall 번호 1 = write
    mov rdi, 1              ; fd = 1 (stdout)
    syscall

    ; --- n-- ; n > 0 이면 계속 ---
    dec rbp
    jnz .loop

    ; --- exit(0) ---
    mov rax, 60             ; syscall 번호 60 = exit
    xor edi, edi            ; status = 0
    syscall

x86-64 리눅스 환경에서 NASM 어셈블리로 작성했다. C의 printf 함수를 사용하지 않고 오로지 시스템 콜만 사용했다. 그리고 그 결과를 확인했다.

$ time ./loop-example-nasm > /dev/null

________________________________________________________
Executed in    1.34 secs      fish           external
   usr time  781.75 millis    0.00 micros  781.75 millis
   sys time  557.94 millis  687.00 micros  557.25 millis

결과를 보고 깜짝 놀랐다. C로 만든 프로그램에 비해 무려 13배나 느리다니! 어떻게 이럴 수가 있는가. 왜 어셈블리가 C보다 느리지?

몇 번을 다시 돌려도 마찬가지의 결과를 얻었다. 여기서 우리는 몇 가지 사실을 알 수 있다. 가장 핵심적인 차이는 바로 I/O 버퍼링(Buffering)과 시스템 콜(Syscall) 횟수의 차이다.

C 언어 코드 (printf)가 더 빠른 이유
#

  • I/O 버퍼링 적용 (시스템 콜 최소화) C 언어의 printf 함수는 내부적으로 표준 출력 버퍼(보통 4KB~8KB 크기)를 사용한다. 숫자를 문자열로 변환한 뒤 바로 Kernel로 보내는 것이 아니라, 메모리 버퍼가 가득 차거나 프로그램이 끝날 때까지 모아두었다가 단 한 번의 write 시스템 콜로 수천 개의 문자를 한꺼번에 출력한다.
  • 최적화된 라이브러리 사용 printf 내부의 정수-문자열 변환 알고리즘은 오랜 시간 동안 고도로 최적화되어 있어 변환 속도 자체도 매우 빠르다.

어셈블리 코드가 느린 이유
#

  • 매 루프마다 시스템 콜 발생 (2,000,000번 호출) 위의 어셈블리 코드는 숫자를 하나 변환할 때마다 syscall (write)을 직접 호출하고 있다.
  • 2백만 번 반복하면서 총 2백만 번의 syscall이 발생한다.
  • CPU가 유저 모드(User Mode)에서 커널 모드(Kernel Mode)로 전환(Context Switch)하는 비용은 생각보다 매우 크다다. 이 전환 작업이 200만 번 누적되면서 엄청난 병목을 일으킨다.
  • div 연산자의 성능 저하 어셈블리 내부의 .convert 루프에서 사용된 div 명령어는 x86 CPU에서 실행 시간이 가장 오래 걸리는 나눗셈 연산 중 하나다. GCC 같은 최적화 컴파일러는 상수(10)로 나누는 연산을 실행할 때 div 대신 비트 시프트와 비트 곱셈(Magic Number Multiplication)을 조합하여 나눗셈 연산을 대체한다.

요약 및 해결 방법
#

어셈블리가 C 언어보다 느렸던 이유는 언어 자체의 차이가 아니라 “어떻게 출력을 처리했는가"의 구조적 차이 때문이다.

만약 어셈블리 코드에서도 몇 KB 크기의 메모리 버퍼를 만들고, 숫자를 변환해 버퍼에 모아두었다가 버퍼가 가득 차면 syscall을 호출하도록 수정한다면 C 언어보다 훨씬 더 빠른 결과를 얻을 수 있을 거다.

어셈블리 최적화 #1 (I/O 버퍼링)
#

위의 NASM 어셈블리 코드를 수정하여 출력 버퍼를 사용하여 I/O를 최적화한 버전을 만들었다. 8KB 크기의 출력 버퍼를 사용하여 syscall을 최소화하고, 숫자 변환 후 버퍼에 모아두었다가 버퍼가 가득 차면 비우는(flush) 방식으로 I/O를 최적화했다. 결과적으로 200만 번 발생하던 시스템 콜이 약 2,000번 수준으로 줄어들어 C 언어와 동등한 성능을 보여준다.

; loop-example-nasm-buffered.asm
; 2000000부터 1까지 역순 출력 (출력 버퍼 사용 버전)

DEFAULT REL                  ; 경고 메시지 방지 (64비트 위치 독립 코드)
BITS 64

BUF_SIZE equ 8192            ; 8KB 출력 버퍼

section .bss
    out_buf resb BUF_SIZE   ; 메인 출력 버퍼
    num_buf resb 16         ; 임시 숫자 변환 버퍼

section .text
    global _start

_start:
    mov r12, 2000000        ; r12 = n (루프 카운터)
    xor r13, r13            ; r13 = out_buf 현재 사용량 (바이트)

.loop:
    ; --- 1. 정수를 임시 버퍼(num_buf)에 ASCII 문자열로 변환 ---
    lea rsi, [num_buf + 15]
    mov byte [rsi], 10      ; 개행 문자 '\n'
    mov rax, r12            ; rax = 변환할 숫자
    mov r8, 10              ; 나누는 수
    mov r9, 1               ; r9 = 변환된 문자열 길이 (개행 포함)

.convert:
    xor edx, edx            ; div 전 상위 64비트 초기화
    div r8                  ; rax = rax / 10, rdx = 나머지
    add dl, '0'
    dec rsi
    mov [rsi], dl
    inc r9
    test rax, rax
    jnz .convert

    ; --- 2. out_buf 공간 점검 및 flush ---
    mov rax, r13
    add rax, r9
    cmp rax, BUF_SIZE
    jle .copy

    ; 버퍼 비우기 (syscall)
    mov rax, 1              ; sys_write
    mov rdi, 1              ; stdout
    lea rsi, [out_buf]      ; buffer
    mov rdx, r13            ; count
    syscall
    xor r13, r13            ; 버퍼 크기 초기화

    ; convert 후 복사할 src 주소 재설정 (sys_write 실행 시 rsi가 변하므로)
    lea rsi, [num_buf + 16]
    sub rsi, r9

.copy:
    ; --- 3. num_buf의 문자열을 out_buf로 복사 ---
    lea rdi, [out_buf + r13]
    mov rcx, r9
    rep movsb
    add r13, r9             ; out_buf 사용량 갱신

    ; --- 4. 루프 제어 ---
    dec r12
    jnz .loop

    ; --- 5. 남은 버퍼 비우기 및 종료 ---
    test r13, r13
    jz .exit

    mov rax, 1              ; sys_write
    mov rdi, 1              ; stdout
    lea rsi, [out_buf]
    mov rdx, r13
    syscall

.exit:
    mov rax, 60             ; sys_exit
    xor edi, edi
    syscall

드디어 C보다 살짝 빠른 결과가 나왔다. 이제 어느 정도 말이 된다. 최소한 이전 코드처럼 어처구니 없는 결과로 사람의 뒷목을 잡게 만들지는 않는다.

하지만 겨우 C보다 이 정도 빠른 걸로는 어셈블리의 면이 서질 않는다. 역시 나눗셈 연산자의 최적화가 필요한 시점이다.

어셈블리 최적화 #2 (연산 최적화)
#

x86-64 CPU에서 div 연산은 수십 사이클을 소비할 정도로 비싼 명령어이지만, Magic Number Multiplication(상수 곱셈을 이용한 나눗셈 대체) 기법을 사용하면 속도를 비약적으로 향상시킬 수 있다. GCC나 Clang 같은 최적화 컴파일러가 10으로 나눌 때 div 대신 사용하는 연산을 어셈블리로 직접 구현하는 방식이다.

10으로 나누기 최적화의 원리
#

\( x / 10 \) 연산은 \( x \) \( \times \) \( \frac{1}{10} \) 과 같다. 이를 고정소수점 표현을 이용해 아래와 같은 정수 연산으로 변환한다.

$$ \left\lfloor \frac{x}{10} \right\rfloor = \left\lfloor \frac{x \times 3435973837}{2^{35}} \right\rfloor $$

64비트 레지스터에서는 상수 0xCCCCCCCCCCCCCCCD를 곱하고 적절히 비트 시프트하는 방식을 사용한다.

핵심 최적화 포인트
#

  • div 연산자 제거: \( x / 10 \) 연산을 무거운 나눗셈 대신 mul rcx와 shr rdx, 3 조합으로 대체
  • 곱셈으로 나머지 계산: 나머지를 구할 때도 나눗셈 대신 몫 * 10을 구한 뒤 원본에서 빼는 방식 사용
  • lea r8, [rax + rax*4] (5배) + shl r8, 1 (2배) = 단 2 클럭만에 10배 처리
; loop-example-nasm-optimized.asm
; 2000000부터 1까지 역순 출력 (64비트 10 나눗셈 최적화 버전)

DEFAULT REL
BITS 64

BUF_SIZE equ 8192

section .bss
    out_buf resb BUF_SIZE
    num_buf resb 16

section .text
    global _start

_start:
    mov r12, 2000000        ; r12 = n
    xor r13, r13            ; r13 = out_buf 현재 사용량

.loop:
    lea rsi, [num_buf + 15]
    mov byte [rsi], 10      ; 개행 문자 '\n'
    mov rax, r12            ; rax = 변환할 값 (n)
    mov r9, 1               ; r9 = 변환된 문자열 길이 (개행 포함)

.convert:
    mov rbx, rax            ; rbx = 원본 값 저장

    ; --- 64비트 10 나눗셈 최적화 ---
    ; rax / 10 = (rax * 0xCCCCCCCCCCCCCCCD) >> 67 (실제로는 rdx >> 3)
    mov rcx, 0xCCCCCCCCCCCCCCCD
    mul rcx                 ; rdx:rax = rax * 0xCCCCCCCCCCCCCCCD
    shr rdx, 3              ; rdx = 몫 (rax / 10)
    mov rax, rdx            ; rax에 몫 저장

    ; --- 나머지 계산: r8 = 원본 - (몫 * 10) ---
    lea r8, [rax + rax*4]   ; r8 = 몫 * 5
    shl r8, 1               ; r8 = 몫 * 10
    sub rbx, r8             ; rbx = 나머지 (0~9)

    ; ASCII 변환 및 버퍼 저장
    add bl, '0'
    dec rsi
    mov [rsi], bl
    inc r9
    test rax, rax
    jnz .convert

    ; --- 버퍼 용량 점검 및 flush ---
    mov rax, r13
    add rax, r9
    cmp rax, BUF_SIZE
    jle .copy

    ; sys_write
    mov rax, 1
    mov rdi, 1
    lea rsi, [out_buf]
    mov rdx, r13
    syscall
    xor r13, r13

    ; syscall 후 rsi 재설정
    lea rsi, [num_buf + 16]
    sub rsi, r9

.copy:
    lea rdi, [out_buf + r13]
    mov rcx, r9
    rep movsb
    add r13, r9

    dec r12
    jnz .loop

    ; 남은 버퍼 비우기
    test r13, r13
    jz .exit

    mov rax, 1
    mov rdi, 1
    lea rsi, [out_buf]
    mov rdx, r13
    syscall

.exit:
    mov rax, 60
    xor edi, edi
    syscall

JIT/VM
#

Python과 Ruby
#

컴파일된 코드의 성능이야 그렇다 치고, 스크립트 언어를 JIT/VM으로 구현하면 얼마나 성능이 좋아지는지도 살펴보지 않을 수 없다. 그리고 그런 성능 향상의 효과를 단적으로 보여주는 것이 바로 파이썬이다.

우선 같은 코드를 Python과 Ruby로 각각 만들었다.

for i in range(2000000, 0, -1):
    print(i)
2_000_000.downto(1) do |i|
    puts i
end

그리고 각각의 실행 결과를 살펴보면,

$ time python3.14 loop-example.py > /dev/null

________________________________________________________
Executed in  887.01 millis    fish           external
   usr time  856.63 millis    0.00 millis  856.63 millis
   sys time    9.69 millis    1.86 millis    7.82 millis

$ time ruby --jit loop-example.rb > /dev/null

________________________________________________________
Executed in    1.31 secs    fish           external
   usr time    1.31 secs  685.00 micros    1.31 secs
   sys time    0.01 secs  260.00 micros    0.01 secs

Python의 버전은 3.14이고 Ruby의 버전은 4.0.6이다. Ruby는 4.0으로 버전업하면서 새로운 JIT를 도입했다는데, 아직 최적화가 안 되어 있어서 거의 효과를 볼 수가 없었다.

#

최적화 기법을 사용한 Chez Scheme보다 훨씬 빠르고, 거의 C언어 수준에 육박하는 성능을 보여준다! C 확장이 잘 안 붙어서 그렇지, 순수 파이썬 코드로 된 라이브러리만 잘 붙이면 PyPy는 정말로 쓸 만한 물건이다. CPython의 개발 속도에 비해 PyPy의 개발 속도가 너무 느리다는 게 안타깝다. 제발 이 훌륭한 프로젝트가 오래 살아남길 바란다.

컴파일된 스크립트 언어
#

그렇다면 컴파일된 스크립트 언어는 어떨까?

Crystal은 자신을 이렇게 소개한다.

“C 수준의 성능과 Ruby의 간결함을 동시에 만족시키기 위해 위한 LLVM 기반 고급(High-Level) 컴파일 프로그래밍 언어.”

정말로 그럴까?

최소한 문법은 Ruby를 닮은 데가 있다.

2_000_000.downto(1) do |i|
 print i
 print '\n'
end

하지만 어쩐 일인지 성능은 파이썬보다 더 느리게 나왔다.

파이썬 문법을 차용한 정적 타입의 컴파일 언어 Nim도 그다지 감동이 없다.

for i in countdown(2000000, 1):
    echo i

두 언의 실행 결과는 나중에 표로 정리하자. 아마도 내가 Crystal이나 Nim에 대해 잘 몰라서, 그래서 최적화 기법을 쓸 수 없어 이런 결과가 나온 게 아닐까 한다. 이 두 언어는 나중에 따로 공부를 해 봐야겠다.

자바스크립트
#

이쪽은 콘솔 입출력에 대해서는 기대하면 안 된다는 게 확실히 드러났다. Node.js와 Bun, Deno로 각각 실행해 보았는데, 예상대로 Bun이 가장 빨랐다. 그리고 Deno가 Node.js보다 빠를 줄 알았는데, 실제로는 그렇지 않았다. Deno가 다른 건 몰라도 콘솔 입출력은 확실히 Node.js보다 느리다는 걸 알게 되었다.

for (let i = 2000000; i > 0; i--) {
    console.log(i);
}
